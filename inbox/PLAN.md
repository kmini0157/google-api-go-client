# Inbox 기획서 — 무료 API로 만드는 "의존 → 구독" 제품

| | |
|---|---|
| **제품명** | Inbox — AI 읽을거리 인박스 (read-it-later) |
| **버전** | v1.0 (2026-07-03) |
| **상태** | MVP 구현 완료 · E2E 23/23 통과 · 보안 감사 22건 수정 반영 |
| **핵심 전략** | 한계비용 ≈ 0 무료 스택 위에서, 사용자의 데이터 자산이 쌓일수록 떠날 수 없게 만들고, 떠나기 아까워진 시점에 구독으로 전환 |

---

## 1. 요약 (Executive Summary)

링크를 저장하면 자동으로 본문 추출 → AI 요약·태깅 → 임베딩되어, **키워드가 아니라 "기억나는 대로" 검색**할 수 있는 개인 읽을거리 인박스.

세 문장으로 요약하면:

1. **비용**: 추출·요약·임베딩이 전부 키 없는 무료 API와 사용자 브라우저에서 실행돼 사용자 1명당 서버 비용이 사실상 0원이다.
2. **의존**: 저장할수록 사용자의 "개인 의미 검색 인덱스"가 자산으로 쌓이고, 이 자산은 다른 서비스로 가져갈 수 없다.
3. **구독**: 월 저장 한도에 도달하는 시점 = 이미 자산이 충분히 쌓여 버리기 아까운 시점이며, 바로 그 순간 페이월이 뜬다.

---

## 2. 전략 논리: 왜 "의존 → 구독"인가

구독을 만드는 것은 기능이 아니라 **전환비용(switching cost)**이다. 사용자가 못 떠나는 이유는 기능이 좋아서가 아니라 **자기 데이터가 쌓여 있어서**다.

```
저장 (마찰 0)  →  자산 축적 (요약+태그+임베딩)  →  검색으로 가치 회수
      ↑                                                    │
      └────────── 주간 다이제스트가 다시 끌어당김 ←─────────┘
```

이 루프가 돌수록:

- **자산 lock-in** — 저장한 글 + AI가 만든 메타데이터(요약·태그·벡터)는 수출해도 다른 곳에서 재현이 안 된다. 검색 품질 자체가 내 데이터량에 비례한다.
- **습관 lock-in** — "일단 Inbox에 넣어" 가 기본 동작이 되면 대체재 검토 자체가 일어나지 않는다.
- **비용 우위** — 경쟁사(Pocket, Readwise 등)는 서버에서 LLM을 돌려 원가가 있지만, 우리는 원가가 0에 수렴해 무료 티어를 무한정 버틸 수 있다. 무료로 오래 버티는 쪽이 데이터를 더 많이 쌓게 하고, 데이터를 더 쌓은 쪽이 이긴다.

---

## 3. 문제와 기회

**문제.** 사람들은 매일 좋은 글을 발견하지만 ① 북마크는 무덤이 된다(다시 안 봄) ② 몇 달 뒤 "그 글 어디 갔지"를 제목 키워드로 찾다 실패한다 ③ 기존 read-it-later는 저장만 해주고 회수(검색·리마인드)를 못 해준다.

**기회.** 2024~25년에 무료 인프라의 임계점이 넘어갔다 — 브라우저 로컬 임베딩(Transformers.js), 키 없는 LLM(Puter.js), 키 없는 본문 추출(Jina Reader), 무료 pgvector(Supabase). **"저장한 모든 것을 의미로 검색"이라는 프리미엄 기능을 원가 0으로 무료 제공**할 수 있는 첫 시점이다.

## 5. 제품 정의

### 핵심 기능 (모두 구현 완료)

| 기능 | 설명 | 사용 스택 |
|---|---|---|
| **원클릭 저장** | URL 붙여넣기 / 모바일 공유 시트(PWA share target) | Jina Reader (키 없음) |
| **AI 요약·태깅** | 저장 즉시 2~3문장 요약 + 주제 태그 자동 생성 | Puter.js (키 없음, 클라이언트) |
| **의미 검색** | "번아웃 관련 그 글" 처럼 기억나는 대로 검색 | Transformers.js 로컬 임베딩 + pgvector |
| **읽음/즐겨찾기/삭제** | 인박스 관리 | Supabase |
| **주간 다이제스트** | 안 읽은 저장분 매주 월요일 메일 리마인드 | CF Worker cron + Resend |
| **매직링크 로그인** | 비밀번호 없음 | Supabase Auth |
| **오프라인 셸** | PWA 서비스워커 | Cloudflare Pages |

### 로드맵 기능 (의존 강화 순)

1. **하이라이트·메모** — 개인 데이터가 더 깊어짐 (M1)
2. **Ask-your-inbox** — 내 저장 코퍼스에 대한 RAG 챗. 이미 있는 임베딩 재활용, 추가 원가 0 (M2)
3. **브라우저 확장 + 단축어** — 저장 마찰 추가 제거 (M2)
4. **"저장한 것과 관련" 재부상** — 임베딩 기반 연관 추천으로 다이제스트 강화 (M3)
5. **공개 컬렉션** — 큐레이션 공유 → 획득 루프 (M4)

## 6. 의존 설계 (Lock-in Architecture)

3개 층으로 설계한다:

**① 자산 층 — 떠나면 잃는 것.**
저장 1건 = 본문 + 요약 + 태그 + 384차원 벡터. 원문 링크는 가져가도 **검색 인덱스와 그 품질은 못 가져간다.** 목표: 가입 후 30일 내 저장 30건(자산 임계점) 도달률 40%.

**② 습관 층 — 매일 오게 만드는 것.**
- 트리거: 주간 다이제스트(월 14:00 UTC), 추후 ntfy 푸시
- 행동: 공유 시트로 3초 저장
- 보상: 검색이 실제로 찾아줌 (가변 보상)
- 투자: 저장·하이라이트가 다음 검색을 더 좋게 만듦

**③ 마찰 층 — 이탈 비용의 비대칭.**
들어오긴 쉽게(매직링크, 키 없음, 무료), 나가긴 아깝게(자산). 단, **데이터 수출은 막지 않는다** — JSON 내보내기를 제공해도 임베딩 검색 경험은 재현 불가이므로 lock-in은 유지되고, "가두는 서비스" 리스크(신뢰 훼손)는 피한다.

## 7. 기술 아키텍처와 비용 구조

```
            ┌─────────────── 브라우저 (PWA) ────────────────┐
 URL 저장 → │  Jina Reader → Puter.js LLM → Transformers.js │
 공유 시트   │    (본문 추출)   (요약+태깅)     (로컬 임베딩)    │
            │                      ▼                        │
            │        Supabase JS (upsert + RLS)             │
            └──────────────────────┬────────────────────────┘
                                   │
                    Supabase (Postgres + pgvector + Auth)
                                   │
                    match_items() RPC ← 의미 검색 (HNSW)
                                   │
            Cloudflare Worker (cron) → Resend 주간 다이제스트
```

### 무료 스택과 한도

| 역할 | 서비스 | API 키 | 무료 한도 | 초과 시 |
|---|---|---|---|---|
| 본문 추출 | Jina Reader | 불필요 | 관대한 rate limit | 키 발급 시 1천만 토큰 |
| 요약·태깅 | Puter.js | 불필요 | 사용자 부담 모델 | — (사용자 측 실행) |
| 임베딩 | Transformers.js | 불필요 | 무제한 (로컬) | — |
| DB·인증·벡터검색 | Supabase | anon 키(공개 안전) | 500MB DB, 5만 MAU | $25/월 |
| 다이제스트 메일 | Resend | 서버 전용 | 3,000통/월 | $20/월 |
| 푸시(예정) | ntfy | 불필요 | 무제한 | — |
| 호스팅 | Cloudflare Pages | 불필요 | 무제한 대역폭 | — |
| 크론 워커 | Cloudflare Workers | 불필요 | 10만 req/일 | — |

### 규모별 월 비용 시뮬레이션

| 지표 | ~1천 사용자 | ~1만 사용자 | ~5만 사용자 |
|---|---|---|---|
| 인프라 비용 | **0원** | Supabase $25 + Resend $20 | ~$100 |
| 필요 유료 전환 | 0명 | **Pro 10명이면 손익분기** | Pro 25명 |

무거운 연산(LLM·임베딩)이 전부 사용자 기기에서 돌기 때문에, 비용은 사용자 수가 아니라 **저장 데이터 총량**에만 비례한다. 이것이 이 기획의 구조적 우위다.

## 8. 수익 모델

### Free vs Pro

| | Free | Pro ($4/월, 연 $36) |
|---|---|---|
| 저장 | **월 30건** (서버 강제: `save_events` 이벤트 계량) | 무제한 |
| 의미 검색 | 전체 제공 (미끼 기능 — 제한하지 않음) | 전체 |
| 주간 다이제스트 | 제공 | 제공 + 연관 추천 |
| Ask-your-inbox (M2) | 월 10회 | 무제한 |
| 하이라이트·메모 (M1) | 제한 | 무제한 |
| 데이터 내보내기 | 제공 | 제공 |

### 페이월 설계 원칙

- **검색은 절대 제한하지 않는다.** 검색이 잘 될수록 자산 가치가 체감되고, 자산 가치가 체감돼야 저장 한도에 지불한다.
- **한도는 이벤트 기준**(삭제-재저장 우회 불가, 서버 RPC로 강제), 재저장(업데이트)은 소모 없음 — 이미 구현·검증됨.
- 페이월 노출 시점 = 월 30건을 쓴 헤비 유저 = 이미 수십 건의 자산 보유자. 전환 논리: *"당신이 쌓은 인덱스를 계속 키우세요."*
- 목표 전환율: 페이월 도달자의 8~12% (자산 보유 상태의 페이월은 일반 SaaS 3~5%보다 높게 잡을 근거 있음).

## 13. 현재 구현 상태 (근거)

`inbox/` 디렉터리, 브랜치 `claude/dev-tools-resources-omsaz9`:

- **구현**: SPA(index/main/app) + Supabase 스키마(pgvector HNSW, RLS, 검색 RPC, 이벤트 계량) + 다이제스트 워커 + PWA(share target, 오프라인 셸)
- **검증**: 실제 헤드리스 Chromium에서 실코드 E2E 23/23 통과 — 로그인, 4건 저장 파이프라인, 의미검색 랭킹(관련 문서 1위·무관 문서 필터), 페이월 강제, 한도 시 재저장 허용, XSS 비실행, 읽음/즐겨찾기/삭제
- **감사**: 적대적 다중 관점 리뷰로 22건 확정·수정 (저장형 XSS 5건, ivfflat→HNSW, 멀티테넌트 recall 붕괴, 다이제스트 1000행 캡, 쿼터 우회 등)
